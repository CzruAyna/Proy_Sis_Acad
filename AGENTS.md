# Instrucciones permanentes del proyecto

Antes de analizar, editar, probar o compilar este proyecto, leer completo
`REGLAS_USUARIO.txt` en la raíz. Es el registro acumulativo de las reglas
expresas del usuario y se aplica a todos los agentes que trabajen aquí.

Conservar las reglas anteriores al incorporar nuevas instrucciones. No
modificar el backend para resolver un cambio de presentación. Consultar los
documentos de coordinación en `docs/` y dejar allí los requisitos pendientes
para el responsable correspondiente.

Para trabajo de backend o de datos institucionales, leer también
`docs/PARA_BACKEND_DATOS_Y_FUENTES.txt` y registrar qué fuentes originales,
documentos e imágenes necesita aportar el usuario y qué falta verificar.

## Recordatorio obligatorio al cerrar cambios

Antes de finalizar cualquier tarea que modifique archivos, volver a leer
completo `REGLAS_USUARIO.txt` y revisar el diff contra todas sus reglas. Esto
se aplica a cualquier tipo de trabajo, incluidos `feat`, `fix`, `refactor`,
`docs`, `chore`, `ci` y cambios similares. Si una regla no se pudo cumplir,
explicarlo y dejar el pendiente para el responsable indicado en `docs/`.

La respuesta final debe indicar qué se modificó, qué comprobaciones se
realizaron y qué quedó sin verificar. La documentación del proyecto se escribe
en Markdown y se enlaza desde `README.md` o `docs/README.md` cuando corresponda.

No incluir en los archivos del proyecto instrucciones para subir, publicar o
empujar cambios a GitHub o GitHub Desktop. Esas indicaciones se entregan solo
por el chat cuando el usuario las solicite.

## Documentación y código libre

Aplicar la [guía de documentación](docs/GUIA_DOCUMENTACION.md) al crear o
actualizar guías, bitácoras y documentos de coordinación. Conservar la
distinción entre estado actual, historial comprobable y pendientes.

El código original y la documentación propia se ofrecen bajo
`GPL-3.0-or-later`, según `LICENSE` y
[`docs/LICENCIA_CODIGO_LIBRE.md`](docs/LICENCIA_CODIGO_LIBRE.md). No sustituir
las licencias de terceros ni agregar restricciones privativas al código
original. Revisar la procedencia y condiciones de los recursos incorporados.

Toda respuesta final debe comenzar con el título del summary del trabajo y
explicar cambios, motivo, comprobaciones realizadas y asuntos sin verificar.
El título se entrega por el chat; no implica crear un commit ni realizar una
operación remota.
